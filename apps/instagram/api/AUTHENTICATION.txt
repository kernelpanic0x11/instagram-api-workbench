OPTIONAL DIRECT MOBILE LOGIN (INSTAGRAPI)

The optional adapter uses https://github.com/subzeroid/instagrapi (MIT) for
authentication rather than maintaining a second mobile login implementation.
No APK, phone connection, browser, or Playwright is needed for this adapter.
Instagram can still require an account challenge or a fresh two-factor code.
The adapter stops on account challenges rather than resolving them automatically.

From the repository root:
  python3 -m venv tools/instagrapi-venv
  tools/instagrapi-venv/bin/python -m pip install -r apps/instagram/scripts/requirements-auth.txt
  npm start --prefix apps/instagram/api

In another terminal, after setting IG_USERNAME and IG_PASSWORD in ~/.secrets:
  tools/instagrapi-venv/bin/python apps/instagram/scripts/connect-instagrapi.py

To enter MFA in a local web form instead of the terminal, add --web-mfa.
Open http://127.0.0.1:8767 and wait until the form requests a code. The form
accepts one code, keeps it only in memory, and displays the verification result.
It expires after five minutes waiting for input and closes shortly after login.

Secrets files are parsed as assignments, never executed as shell scripts.
Two-factor codes are requested with hidden terminal input. The adapter verifies
the account username before importing its session, then asks the workbench to
verify the numeric account identity independently. Output omits account details.
Session settings are saved outside the repository with private permissions.
On macOS: ~/Library/Application Support/mobile-api-workbench/auth/instagram.json.
On Linux: $XDG_DATA_HOME/mobile-api-workbench/auth/instagram.json (default
~/.local/share). These settings contain credentials; do not share them.
Subsequent runs load those settings and let instagrapi validate/reuse the session.
The local proxy holds imported credentials only until disconnect or shutdown;
Disconnect does not delete the adapter's saved session file.
Live acceptance depends on Instagram; synthetic adapter tests do not prove login.

BROWSER LOGIN (ALTERNATIVE)

Install Google Chrome and run npm ci in api. Open Instagram login creates a
separate non-persistent Chrome context through optional Playwright 1.64.1.
Sign in directly on Instagram; the workbench does not collect passwords or OTPs.
Then Verify authentication and GET my account settings run through same-origin
browser fetch with the browser's own cookies and CSRF header. Cookies are not
exported to the Node proxy and storageState is never saved. Closing the browser
or Disconnect ends this local session. No personal Chrome profile is attached.
Redirects are not followed by browser API requests. Responses are limited to
32 MiB and requests to 30 seconds. This text/JSON transport does not support
binary uploads. API compatibility and Instagram's login acceptance can vary.
A user login is still needed to complete a live test of this new browser flow.

ADVANCED MANUAL CREDENTIALS

AUTHENTICATION CHECK

Browser mode uses GET /api/v1/accounts/edit/web_form_data/ on www.instagram.com
with web app headers. Verification requires HTTP 200, JSON status=ok, and private
form_data containing a username and account-settings fields. Only the username
is returned: email, phone, birthday and other private fields are discarded.
This endpoint does not supply a numeric ID, so identityMatch is unavailable.
An expected numeric ID is not verified in Browser mode.

Android mode uses GET /api/v1/accounts/current_user/?edit=true on i.instagram.com.
It requires status=ok and a numeric current-account ID and username. When an
expected ID is available from credentials or explicit input, it must match.

Both modes reject login/challenge responses, arbitrary HTTP 200 responses,
and public profile data. Up to two canonical redirects are allowed only to
the same origin and account endpoint. Unknown redirect paths are redacted.
Checks apply at the recorded time, not indefinitely or to every API permission.
Reconnect/disconnect clears verification and pending stale results are discarded.
Credentials remain in process memory only. No credentials are persisted here.

Browser verification was confirmed with a live authenticated settings GET.
The former browser current_user request returned useragent mismatch; that
Android endpoint is no longer used to verify browser sessions.
Tests also cover synthetic successes, failures, redirects and privacy filtering.

MOBILE HTTP TRANSPORT
When tools/instagrapi-venv/bin/python exists, restarting the local server enables
the optional mobile HTTP/2 worker for Android-profile requests. The worker uses
connection credentials in memory; it never logs in or saves sessions. Browser
requests keep their existing transport. See ../docs/MOBILE-TRANSPORT.md for the
paired HTTP-400/HTTP-200 evidence and limits.
